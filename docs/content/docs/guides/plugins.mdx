---
title: Package routes as a plugin
description: Package the routes, middleware, and state of one feature as an Air plugin that stays in its own scope.
---

A plugin is a def that returns a route list. It packages the routes,
middleware, and state of one feature. The app decides where to mount it.
Air has no plugin API: the rules in this guide come from how routes work.

## Write a plugin

This plugin adds a status page and a visit counter. Each response of the
plugin gets `cache-control: no-store`:

```python
def no_cache(req: Air.Request(), res: Air.Response()) -> IO(Air.Response()):
  IO.pure(Air.Response(), Air.Response.with_header(res, "cache-control", "no-store"))

def status(req: Air.Request()) -> IO(Air.Response()):
  IO.pure(Air.Response(), Air.Response.json("{\"status\":\"ok\"}"))

def visits.fin(n: U32) -> IO(Air.Response()):
  IO.pure(Air.Response(), Air.Response.text(U32.show(n)))

def visits(req: Air.Request()) -> IO(Air.Response()):
  IO.bind(U32, Air.Response(), Air.Store.incr(req, "status_plugin", "visits"), visits.fin)

def status_plugin(+prefix: String) -> List<Air.Route()>:
  Air.Route.mount(prefix, Air.Route.wrap(~Air.on_send(no_cache), [
    Air.Route.get("/", status),
    Air.Route.get("/visits", visits)
  ]))
```

## Add a plugin to an app

To add a plugin, put its route list in `Air.Route.all` with the other
route lists:

```python
def routes() -> List<Air.Route()>:
  Air.Route.all([
    app_routes(),
    status_plugin("/status")
  ])
```

## Keep a plugin in its own scope

Follow these rules, so that a plugin does not change the rest of the app:

1. **Wrap only the plugin routes.** `Air.Route.wrap(~mw, routes)` applies
   `mw` to those routes only. A hook or an auth check in a plugin does
   not run for the other routes of the app.
2. **Take the prefix as an argument.** `Air.Route.mount(prefix, routes)`
   puts every route of the plugin under `prefix`. The app decides where
   the plugin lives.
3. **Name the store namespace after the plugin.** All plugins share the
   store, so use a namespace such as `status_plugin`. Do not use the
   namespaces that Air reserves. See
   [Reserved namespaces](/docs/reference/state#reserved-namespaces).
4. **Put a prefix on request locals.** Name a request local
   `status_plugin.user`, not `user`.
5. **Check for conflicts at startup.** Call `Air.Route.check(routes())` in
   `main`. It ends the process when two plugins add the same method and
   pattern.

## Give a plugin a setting

A plugin that needs a setting takes it as an argument, like `prefix`. When
the setting changes for each deployment, read it in the handler with
`Air.Config.get`. The app is a closed template, so a value that `main`
reads cannot reach the plugin. See
[Configure Air from the environment](/docs/guides/configuration).

## Share values with plugin handlers

Air has no `decorate`. A plugin shares values with its handlers through
request locals and the store.
