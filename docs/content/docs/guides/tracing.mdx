title: Tracing
description: W3C trace context, one span per request, and an exporter you pick.
---

In a system of several services, the W3C `traceparent` header carries
a request's trace across services. `Air.trace` makes an Air service
follow the header. If the request has a valid `traceparent`, Air
continues that trace. If it does not, Air starts a new trace. Air gives
the ids to your handlers, and after each request it gives one span to
an exporter function that you choose.

```python
def app(req: Air.Request()) -> IO(Air.Response()):
  Air.use([
    Air.request_id,
    Air.trace(Air.Trace.print),
    Air.log
  ], base)(req)
```

Put `Air.trace` inside `request_id` and outside `log`. Then each log
line gets a `"trace_id"` field, and you can join the log with the
traces of the services around it.

## The header

A valid value looks like
`00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`. It has four
parts: the version, the trace id, the caller's span id and the flags.
The hex digits must be lowercase, and neither id can be all zeros. The
version `ff` is invalid. A version above `00` is read by its first four
fields only. Any other value starts a new trace, the same as a request
without the header.

## What handlers see

The ids are request locals:

| Local | Value |
| --- | --- |
| `trace_id` | 32 hex characters, the caller's or a new random one |
| `span_id` | 16 random hex characters, this request's span |
| `parent_id` | The caller's span id, `""` for a new trace |
| `trace_flags` | `01` when sampled, `00` when not |
| `traceparent` | The value to send to a service you call: `00-<trace_id>-<span_id>-<flags>` |
| `tracestate` | The caller's `tracestate` header, unchanged |

When a handler calls another service, send
`Air.Request.local(req, "traceparent")` as that request's `traceparent`
header, so the next service continues the trace under this span.

## Spans

After the response, `Air.trace` builds an `Air.Span()` and passes it to
the exporter:

| Field | Value |
| --- | --- |
| `name` | `GET /users/:id`, from the route pattern ([metrics](/docs/guides/metrics) use the same label). Only the method, when no route answered. |
| `start_ms` | Unix epoch milliseconds, as text |
| `duration_ms` | Milliseconds spent in the rest of the chain |
| `status`, `method`, `route`, `path` | The request and its answer |

`Air.Trace.print` writes each span as one JSON line on stdout. The
attribute names follow OpenTelemetry's HTTP conventions:

```json
{"trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"a1b2c3d4e5f60718","parent_span_id":"00f067aa0ba902b7","name":"GET /users/:id","start_time_unix_ms":1790000000000,"duration_ms":3,"http.request.method":"GET","http.route":"/users/:id","url.path":"/users/7","http.response.status_code":200}
```

An OpenTelemetry Collector can read these lines from the log, for
example with the filelog receiver. `Air.Trace.drop` exports nothing,
but still reads and passes on the ids.

An exporter is any `Air.Span() -> IO(Unit)`. A span's fields are read
with `Air.Span.trace_id(s)`, `Air.Span.name(s)` and so on. You can build
a span of your own with `Air.Span.new(...)` and pass it to the same
exporter.

## Sampling

A continued trace follows the caller's sampled flag. A new trace is
always sampled by `Air.trace`. `Air.trace_sampled(10, exporter)` keeps
one new trace in ten instead. The decision is made from the last eight
hex digits of the trace id, so every service that samples this way
makes the same choice for a given trace. Requests that are not sampled
still get ids and a `traceparent`, but their span is not exported.

## Cost

Ids come from the host's random source, and each draw costs about as
much as a system call. Continuing a trace takes two draws, for the
span id. Starting one takes six: four for the trace id and two for the
span id. `bench/README.md` has the measured cost (see
[benchmarks](/docs/project/benchmarks)).

OTLP export over the network is [not built yet](/docs/project/not-yet).
